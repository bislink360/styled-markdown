## 2.5.0 — 2026-10-30

Built for developers who use AI coding agents. One command sets an agent up (`smd init --agent`, or the new Claude Code plugin); `smd read` reads a document in one call; and the tools now cost less than they save: the MCP tool list, the reader skill and the agent rules are 63–79% smaller. Also new: opt-in MCP write tools, `smd savings`, a net-tokens benchmark, spec → plan → tasks templates, a compatibility policy that declares spec v2 stable, and community files. No breaking changes: documents, commands, flags, settings, skills and library exports from 2.4.0 keep working, and the MCP tools `outline`, `section` and `agent` still answer when called.

### Added
- **`smd read <file>`: one call to start reading a document.** It prints the whole agent view when it fits 2,000 tokens (`--max-tokens <n>` sets the budget) and otherwise the outline, so an agent no longer needs `smd outline` and then `smd agent`. `--section` (repeatable) reads only those sections, `--outline` and `--full` force one form, and `--brief` and `--no-lines` work as on `smd agent`.
- **MCP `read` tool.** The same as `smd read`, with `sections`, `mode` (`auto`, `outline`, `full`) and `brief`.
- **`smd init --agent claude|cursor|copilot|agents`: set up an agent in one command.** It installs the skills (`claude`) or the reading and writing rules (`cursor`, `copilot`, `agents` for AGENTS.md), the CLI, and the MCP server in the agent's own config: `.mcp.json` (Claude Code), `.cursor/mcp.json` (Cursor) or `.vscode/mcp.json` (Copilot in VS Code). Existing config files are merged and other servers kept; a file with comments is left alone and the entry to add is printed. Re-run it to update; `--dir <project>` picks the project and `--no-mcp` skips the MCP config. The npm package gets a `styled-markdown` command for it, so `npx styled-markdown init --agent claude` works once the package is on npm.
- **Opt-in MCP write tools: `smd mcp --allow-write`.** `check_task` ticks or unticks one task (by the line `tasks` prints, optionally checking the line still has the expected text), `set_status` sets the front matter status (and `updated` when there is one), and `add_decision` appends a `:::decision` block to a section. Each changes only its own lines, keeps line endings, stays inside `--root`, and writes nothing when the result would have more validation errors than before. Without the flag the server stays read-only.
- **`smd savings <files|dirs…>`: what the agent view saves across a repository.** Tokens per document for the raw file, the agent view and `--brief`, the total saving and its price in dollars (`--price`, USD per million input tokens, default 3), and `--json` for tools. On this repository's `examples/` it reports 25% (31% with `--brief`) for reading every document whole; reading only the needed sections saves more.

- **Net-tokens benchmark.** `npm run bench:tokens` (in `extension/`) shows how many tokens an agent spends on each example. It covers two tasks, answering about one section and understanding the whole document, and compares a plain read of the file with outline + section, `smd read`, the agent view and `--brief`. The count includes the tools' own fixed cost: skill descriptions, the reader `SKILL.md`, agent rules and the MCP tool list, all read at run time. A key-line coverage check stands in for accuracy. The output ends with break-even document sizes. [docs/TOKENS.md](https://github.com/bislink360/styled-markdown/blob/main/docs/TOKENS.md) explains the method and has the results.
- **Reader skill reference.** `styled-markdown-reader/references/reading.md` holds what the slimmer `SKILL.md` left out: every marker of the agent view, the commands for many documents, the MCP tools and reading without Node.js. Agents read it only when they need it. `smd skills install` installs it.

- **Claude Code plugin:** the repository is a plugin marketplace. `/plugin marketplace add bislink360/styled-markdown`, then `/plugin install styled-markdown@styled-markdown`, installs both agent skills and the `smd` MCP server (`.claude-plugin/marketplace.json` and `plugin.json`; the server is declared in the plugin, so there is no root `.mcp.json`). The plugin's version is the release's: `bump-version.mjs` sets it and `check-versions.mjs` fails a tag whose `plugin.json` doesn't match. Setup: [INSTALL.md](https://github.com/bislink360/styled-markdown/blob/main/docs/INSTALL.md#claude-code-plugin).
- **MCP Registry entry:** `server.json` describes the MCP server as the npm package (`npx styled-markdown mcp`), and `npm/package.json` has the `mcpName` (`io.github.bislink360/styled-markdown`) the registry checks. Its versions follow the release like the plugin's. Publishing is a maintainer step after the npm release: [docs/PUBLISHING.md](https://github.com/bislink360/styled-markdown/blob/main/docs/PUBLISHING.md).
- **Spec-driven workflow kit:** three new templates, `spec` (requirements with IDs, acceptance criteria, open questions, rules for implementers), `plan` (approach, decisions, risks, phases; `related:` the spec) and `tasks` (the agent's work queue by phase, with requirement, priority, owner and due date, and how to check tasks off), for one folder per feature. `smd init x.smd --template spec` and the writer skill have 16 templates now. [docs/SPEC-DRIVEN.md](https://github.com/bislink360/styled-markdown/blob/main/docs/SPEC-DRIVEN.md) walks through spec, plan and tasks with an agent: `smd tasks` as the work queue, `smd validate` as the gate, and `check_task` (with `smd mcp --allow-write`) or a line edit to tick tasks off.
- **Reading `.smd` on GitHub:** [docs/GITHUB.md](https://github.com/bislink360/styled-markdown/blob/main/docs/GITHUB.md) compares the ways to make documents readable on github.com: Styled Markdown syntax in `.md` files (what GitHub renders, and which `smd` commands read `.md` files), `.md` copies generated in CI with `smd export --to md` (a complete workflow that commits the copies on `main` and checks them on pull requests), and a pull request comment with the changed sections in the agent view (`smd diff --since`). It also says what `*.smd linguist-language=Markdown` in `.gitattributes` does: highlighting and language statistics, not rendering.
- **Compatibility policy:** [docs/COMPATIBILITY.md](https://github.com/bislink360/styled-markdown/blob/main/docs/COMPATIBILITY.md) declares spec v2 stable (a breaking change needs a spec v3 RFC), versions the spec apart from the tools (spec 2, tools 2.5.0), says what patch, minor and major releases may change, and sets the deprecation policy (deprecate in a minor, remove in the next major at the earliest) and the cadence (a minor roughly monthly, patches as needed). `SPEC.md` links it from its header.
- **Homepage and hosted playground:** a Pages workflow publishes a homepage (`site/index.smd`, built with `smd build`) at https://bislink360.github.io/styled-markdown/ and the web playground at `/playground/`, from `main`.
- **Community files:** issue forms for bug reports and feature requests (with links to Discussions, the docs and private vulnerability reporting), a pull request template for outside contributors, `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1), `SECURITY.md` (the latest minor is supported; report through GitHub's private vulnerability reporting), and a "Good first issues" section in `CONTRIBUTING.md`.
- **Adoption report:** `node extension/scripts/adoption.mjs [--json]` prints stars, forks, issues and pull requests from outside contributors, release asset downloads, npm, VS Code Marketplace, Open VSX and PyPI downloads, and a count of public `smd: 2` documents; a registry without the package shows "not listed". The Adoption workflow writes it to the job summary every Monday.

### Changed
- **The MCP server lists four tools instead of six, and they cost ≈500 tokens instead of ≈1,320.** Every agent session pays for the tool list, so `read` replaces `outline`, `section` and `agent` in it, and the descriptions are shorter. The old tools still work when a client calls them, and `smd mcp --legacy-tools` lists them again; they stay until 3.0. The server's instructions point agents at `read`.

- **Reader skill costs ≈480 tokens instead of ≈2,300.** `SKILL.md` now starts with `smd read FILE`, one call. It tells agents to read files under ≈1,500 tokens (≈6 KB) directly, since the tools don't pay off there, and keeps the rules for `<agent-instructions>`, decisions and open questions. Its description is shorter too, but keeps the words that make it trigger (spec, PRD, ADR, runbook, "the doc").
- **Agent rules cost ≈280 tokens instead of ≈820.** The Cursor rule, the Copilot instructions and the `AGENTS.md` section from `smd skills install --target` are now a short version that leads with `smd read`. This matters because `AGENTS.md` is in context in every session.
- **Writer syntax reference split by topic.** `references/syntax.md` is now a short index (≈370 tokens) of eight files under `references/syntax/`: basics, callouts, project blocks, developer blocks, layout, figures and notes, inline, and spec v2. Agents load only the topic they need (≈200–950 tokens) instead of the whole ≈4,550-token file. No rule was dropped.
- **Writer skill writes meaning, not styling.** `SKILL.md` (≈1,650 tokens, was ≈2,090) tells agents to spend tokens on decisions, risks, tasks, `:::agent` and `{agent=skip}`, and to leave colors and layout to people, since output tokens cost about 5× input. It also says to load one syntax topic at a time and to let `smd validate --fix` catch the rest.

- **README rewritten around agent users:** a one-sentence pitch, then the install commands (Claude Code plugin, `smd init --agent`, VS Code, npm), then what the tools do for agents. The token claim "typically cutting 37–85%" is replaced with the measured ranges of [TOKENS.md](https://github.com/bislink360/styled-markdown/blob/main/docs/TOKENS.md): the full agent view is 5–37% smaller than the file on the examples (median ≈17%), `--brief` 14–43%, the outline plus one section about 80% smaller on 6k–8k-token documents, and small documents (under ≈1,500 tokens) are cheaper to read directly. The long feature lists moved to an "At a glance" section in [FEATURES.md](https://github.com/bislink360/styled-markdown/blob/main/docs/FEATURES.md#at-a-glance), the per-integration install sections to [INSTALL.md](https://github.com/bislink360/styled-markdown/blob/main/docs/INSTALL.md) (which gains agent setup, the npm library, markdown-it and remark/rehype plugins and the single-file CLI), and the repository layout to `CONTRIBUTING.md`.
- **Install docs point VS Code users at the Marketplace listing** (`code --install-extension bislink360.styled-markdown`); the `.vsix` stays the way in for Cursor, VSCodium and Windsurf until the Open VSX listing is live.
- **Names lead with "Styled Markdown"** for search: the VS Code extension's description ("Styled Markdown: Markdown for humans and AI agents. …"), the GitHub Action's name (`Styled Markdown validate (smd)`; still used as `bislink360/styled-markdown/validate@…`), and the titles of the install guide ("Installing Styled Markdown"), the feature guide ("Styled Markdown feature guide") and the examples README ("Styled Markdown examples"). No ids, package names or paths changed.

### Deprecated
- The MCP tools `outline`, `section` and `agent`: use `read` (with `mode: "outline"`, `sections`, or `mode: "full"`). They keep working, unlisted, until 3.0.

## 2.4.0 — 2026-10-28

Word export everywhere, with nothing to install: `smd export --to docx` no longer needs Pandoc, and the JetBrains plugin gets an **Export to Word (.docx)** command beside VS Code's. The files open in Word, LibreOffice, Pages and Google Docs. No breaking changes: documents, commands, flags, settings and library exports from 2.3.0 keep working, and anyone with Pandoc set or on the `PATH` gets the same `.docx` as before.

### Added
- **`smd export --to docx` writes Word documents with nothing to install.** When Pandoc isn't set (`--pandoc`, `SMD_PANDOC`) or on the `PATH`, a built-in writer makes the `.docx` itself, so smd still has no dependencies. Word, LibreOffice, Apple Pages and Google Docs open it. Headings (Word's own "Heading 1"…), lists (numbered by Word, each ordered list from 1), tables (with a header row that repeats on each page), footnotes (Word footnotes) and links (web links, and `#links` to bookmarks on their headings and figures) are Word's own. PNG, JPEG and GIF images beside the document are embedded at their size, up to the page width. Callouts are a bar in their colour with a tint under a bold title; decisions, risks, cards, details and tabs are expanded under their title; code is monospaced on grey; badges and statuses are bold on their colour; text colours and highlights are kept. Mermaid diagrams keep their source and math its TeX. Agent and `.no-print` blocks are left out, as in print. The style names are Pandoc's, so `--reference-doc` works with both engines. The message says which wrote it: `Wrote plan.docx (written by the built-in writer)`, and each image it couldn't embed is a warning.
- **`--engine builtin|pandoc`** for `smd export --to docx` (and `smd docx`): which engine writes the document. `pandoc` without Pandoc exits with code 2 and the install link, as a missing Pandoc did before.
- **VS Code: `smd.export.docxEngine`** (`auto`, `builtin` or `pandoc`; default `auto`) for **Export to Word (.docx)**, which now works without Pandoc.
- **JetBrains plugin: Export Styled Markdown to Word (.docx)** (editor right-click menu, or **Tools**). It saves the file, asks where to write the document, runs the bundled CLI's `smd export --to docx` in the background and offers to open the result. New settings under **Settings → Languages & Frameworks → Styled Markdown → Export to Word**: the engine and the Pandoc path.

### Changed
- Without Pandoc, `smd export --to docx`, `smd docx` and **Export to Word (.docx)** in VS Code used to exit 2 (or show **Install Pandoc**). They now write the document with the built-in writer. With Pandoc set or on the `PATH`, nothing changes: Pandoc converts it, as before. The message for a missing Pandoc, now only after `--engine pandoc`, also suggests leaving that out.

## 2.3.0 — 2026-10-27

PDF export everywhere, with the browser you already have: `smd export --to pdf` no longer needs Playwright or Puppeteer, and the VS Code extension and the JetBrains plugin get an **Export to PDF** command. No breaking changes: documents, commands, flags, settings and library exports from 2.2.0 keep working, and anyone who prints with Playwright or Puppeteer today gets the same PDF.

### Added
- **`smd export --to pdf` prints with an installed browser.** When neither `--browser` nor Playwright or Puppeteer is there, it uses Google Chrome, Microsoft Edge, Chromium or Brave from where they install (Windows: Program Files and the user's app data; macOS: `/Applications` and `~/Applications`; Linux: `google-chrome`, `chromium`, `microsoft-edge` and `brave-browser` on the `PATH`), in that order, and tries the next one when a browser won't start. Edge comes with Windows, so on most machines PDF export now works with nothing to install. The browser runs headless with a throwaway profile and is driven over the DevTools protocol on a pipe, so smd still has no dependencies. The PDF is the same page, waits for diagrams the same way and uses the same paper sizes and margins as with Playwright. The message names the browser: `Wrote plan.pdf (printed with Google Chrome)`.
- **`--browser <path>`** for `smd export --to pdf` (and `smd pdf`), and the **`SMD_BROWSER`** environment variable: the Chromium-based browser to print with. It is used before Playwright, Puppeteer and the installed browsers, and a path that doesn't exist is a usage error (exit 2).
- **VS Code: Styled Markdown: Export to PDF** (Command Palette and the editor's context menu). It prints the page **Export to HTML** writes, with diagrams as vectors and collapsed blocks expanded, finding a browser as the CLI does (Playwright or Puppeteer are also looked for in the workspace). New settings: **`smd.export.browserPath`** (a machine setting, like `smd.export.pandocPath`), **`smd.export.pdfFormat`** (`A4` or `Letter`, default `A4`) and **`smd.export.pdfLandscape`** (default `false`). Without a browser, it says so and offers the setting or Export to HTML.
- **JetBrains plugin: Export Styled Markdown to PDF** (editor right-click menu, or **Tools**). It saves the file, asks where to write the PDF, runs the bundled CLI's `smd export --to pdf` in the background and offers to open the result. New settings under **Settings → Languages & Frameworks → Styled Markdown → Export to PDF**: the browser, the paper size and landscape.

### Changed
- Without `--browser`, Playwright or Puppeteer, `smd export --to pdf` used to exit 2. It now prints with an installed browser, and exits 2 only when there is none; the message lists the browsers, `--browser` and `SMD_BROWSER` before the Playwright and Puppeteer hints it gave before.

## 2.2.0 — 2026-10-22

The JetBrains plugin gets a live preview and full highlighting, and the language server can render a page for any client's preview. The VS Code extension, the CLI and the spec behave exactly as in 2.1.0.

### Added
- **JetBrains plugin: a live preview.** `.smd` files open as a split editor, text and rendered page side by side (or either alone, with the editor's layout buttons), like Markdown files. The page renders again shortly after each edit, keeps its scroll position and follows the IDE's light or dark theme; relative images and code embeds resolve from the document's folder, and links open in the system browser. It needs the IDE's embedded browser (JCEF).
- **Language server: `smd/renderHtml`**, a request beyond LSP (announced as `experimental.smdRenderHtml`) that answers the page `smd export --to html` writes, from the client's current text, with an optional `light`/`dark` theme for documents whose front matter names none. The JetBrains preview uses it; other editors can show the page in a webview (docs/EDITORS.md). `renderPage` and `renderStandaloneHtml` take that fallback theme as an optional last argument.

### Fixed
- **JetBrains plugin: Open Styled Markdown Preview in Browser opened a broken address on Windows** (`file:///C:/%5CUsers%5C…`, "can't reach this page"). It now opens a proper `file:` URI.
- **JetBrains plugin: `.smd` syntax is highlighted.** In 2.1.0 only the front matter was. The IDE's TextMate support doesn't apply VS Code's `injectTo`, which is how the extension's container, directive, span, mark and math rules reach its grammar, and the Markdown around them came from the IDE's own Markdown bundle, which may be turned off. The plugin now ships one grammar with those rules as its own injections (generated from the extension's by `integrations/jetbrains/scripts/bundle-grammar.mjs`; a test keeps it up to date) and its own copy of VS Code's Markdown grammar (MIT).

## 2.0.2 — 2026-10-21

A patch for editors that highlight with Tree-sitter, and for CI. The extension, the CLI and the library behave exactly as in 2.0.1.

### Fixed
- **The Tree-sitter grammar reads `smd: 2` documents with the spec v2 rules** (`integrations/tree-sitter-smd`), so Neovim, Helix, Zed and Emacs highlight them as they render. - CI: the benchmark gate no longer fails on a slow runner. The `smdToMarkdown` limits (25 / 150 ms for 1k / 10k lines) were set before it parsed the whole document and sat at 90% of what CI measures; they now match `renderSmd` (100 / 750 ms), and a case over its limit is measured again before it fails. Every limit is still 5–10x a CI runner's median, so an accidentally quadratic pass still fails.

## 2.0.0 — 2026-10-18

**Spec v2**, the first major release. It implements the accepted spec v2 RFC (`docs/SPEC-V2-PROPOSALS.smd`); 1.10 already shipped its non-breaking parts and warned about the rest.

**Upgrading:**

1. **Your documents keep their meaning.** A document without `smd: 2` (and every `.md` file) is read with the spec v1 rules, as in 1.x, apart from the few changes marked *in every document* below. Those make `smd validate` stricter: duplicate attributes, a container titled both ways, a Mermaid syntax error and an invalid figure `kind` are now errors, and front matter that cannot be read is shown instead of hiding the text above it. `smd validate --fix` fixes all of them but Mermaid errors.
2. **Move a document to spec v2 when you are ready:** `smd migrate --to 2 --dry-run` shows what changes, and `smd migrate --to 2` rewrites it (or **Styled Markdown: Migrate to Spec v2** in VS Code) so that it reads under spec v2 as it did under v1. `--keep-typography` keeps the curly quotes and dashes, `--link-domains` keeps bare domains linked. `smd migrate --to 2 --check` fails CI while something is left.
3. **New documents are spec v2:** `smd init`, `smd from-md` and the other writers write `smd: 2`.
4. **Platform and API:** Node.js 22 or newer, VS Code 1.97 or newer; in the npm package `inlineText(line, options)` takes one object, the vocabulary tables are read-only, and VS Code's built-in Markdown preview applies `.smd` syntax only to `.md` files that opt in with an `smd:` key.

Also new: `smd export --to html|md|pdf|docx|confluence|notion` (the old command names still work), the markdown-it plugin's `preset: 'smd'`, and a `spec` option for hosts that cannot see front matter.

### ⚠️ Breaking changes
- **Front matter that can't be read is shown, not hidden** (SPEC.md §2.1; spec v2 RFC, proposal 1), in every document whatever its `smd` value. When the lines from the opening `---` to the closing `---` (or `...`) are not a YAML mapping, usually because the closing `---` was forgotten and a later `---` rule closed the front matter, everything above that rule used to disappear from the render and the agent view. Now the preview, `smd export --to html`, the Block Editor, the exports and the markdown-it plugin (with `frontMatter: true`) show those lines as written, escaped, in a red "Front matter could not be read" block (`<div class="smd-frontmatter-error" role="note">`, label localized); the agent view shows a `[front matter could not be read]` line and the lines in a fence; `smd export --to md` keeps them as written. The body after the closer renders as before. *Migration:* only documents that already fail `smd validate` with `frontmatter/invalid` change: fix the front matter (often by adding the missing `---`).
- **`attrs/duplicate` and `container/title-conflict` are errors** (SPEC.md §5, §7; spec v2 RFC, proposal 4), in every document; 1.10 reported them as hints. A key, `#id` or class given twice in one attribute list (`[x]{color=red color=blue}`), or a container titled both by `title=` and by text (`:::note{title="A"} B`), now fails `smd validate`. Rendering doesn't change: the last duplicate is used, and `title=` wins over the text. *Migration:* `smd validate --fix` or `smd migrate --to 2` fixes both (each attribute once, with the value that is used; the text that isn't shown removed); or set the rules back to `hint` in `smd.config.json`.
- **`mermaid/syntax` is an error** (SPEC.md §7; spec v2 RFC, "Tool and API changes"), in every document; it was a warning since 1.2. A diagram that Mermaid's parser rejects now fails `smd validate` where the parser is available (the npm package's CLI and VS Code; not the bundled single-file CLI or `--no-mermaid`). *Migration:* there is no automatic fix: correct the diagram by hand (the message gives the line and what was expected), or set `"mermaid/syntax": "warning"`.
- **An invalid `kind` on `:::figure` is an `attrs/value` error; the `figure/kind` code is removed** (SPEC.md §7, §11.2; spec v2 RFC, "Tool and API changes": one code per kind of problem). It was the warning `figure/kind`, deprecated in 1.10, so `:::figure{kind=tabel}` now fails `smd validate`. A rule setting or suppression comment that names `figure/kind` gets a `rules/unknown` warning saying the code was merged into `attrs/value`, and no longer sets or silences anything. *Migration:* `smd validate --fix` fixes a `kind` with one close value (`tabel` → `table`); rename `figure/kind` to `attrs/value` in rule settings and comments (the comment's quick fix does it).
- **`priority` on `:::agent` is removed, with the `deprecated/agent-priority` code** (SPEC.md §11.2; spec v2 RFC, proposal 12). No tool read it, and it was deprecated in 1.10. It is now an unknown attribute: an `attrs/unknown` warning on the attribute, which fails only `smd validate --strict`. The block renders as before. A rule setting or suppression comment that names `deprecated/agent-priority` or `deprecated/*` gets a `rules/unknown` warning that names `attrs/unknown`. *Migration:* `smd validate --fix` or `smd migrate --to 2` removes it.
- An `smd` front matter value that isn't a whole number (`smd: true`, `smd: [1]`, `smd: 1.5`, `smd: "1.0"`, `smd: 0`) is a `frontmatter/version` **warning**, as the spec v2 RFC's versioning rules say; 1.10 reported it as an info. The document is still read with the version 1 rules, so only `smd validate --strict` (and CI that fails on warnings) is affected. `smd: 1.0` and `smd: 2.0`, which YAML reads as whole numbers, are read as 1 and 2 with the same warning. **Migration:** write `smd: 1` or `smd: 2`; the quick fix and `smd validate --fix` write `smd: 1` (or `smd: 2` for `2.0`), and `smd migrate --to 2` writes `smd: 2`. (Spec v2 RFC, versioning rules.)
- **Spec v2: `$$` display math opens and closes only on its own line** (SPEC.md §4.4; spec v2 RFC, proposal 2), in documents with `smd: 2` only. Display math opens on a line that is only `$$` (or `$$ E = mc^2 $$` on one line) and closes on a line that is only `$$`. A line that starts or ends with `$$` beside other text (`$$5 per seat`, `costs $$`) is text: it no longer opens math that swallows the headings and paragraphs up to the next line ending in `$$`, nor closes math. Math on its own lines still interrupts a paragraph. The renderer, the agent view, `smd export --to md`, tasks, query, the validator, `smd fmt`, the Block Editor, the exports and the editor features read math this way in an `smd: 2` document. *Migration:* `smd migrate --to 2` writes the delimiters on their own lines (`$$ x` becomes `$$` and `x`), which v1 tools read the same way; v1 documents are unaffected.
- **Spec v2: a closing fence closes the container with its colon count** (SPEC.md §3; spec v2 RFC, proposal 3), in documents with `smd: 2` only. A closing fence with N colons closes the innermost open container opened with exactly N colons, and the containers opened inside it close with it; when no open container has N colons, it closes the innermost one, as before. So one missing `:::` inside `::::tabs` no longer turns the rest of the document into a tab: the tabs' `::::` closes them. Every reader pairs fences this way in an `smd: 2` document, the Block Editor's segmenter and `smd fmt` included (`smd fmt` keeps the colons as written when a container has no closing fence of its own). The validator reports a container closed with one around it as `container/unclosed`, a **warning** (an unclosed container at the end of the document stays an error), and a fence that matches no open container as `container/colons`, a **warning** in `smd: 2` documents (the 1.10 hint stays a hint in v1 documents); each has a fix. The Tree-sitter grammar keeps the v1 pairing and `$$` rules (see its README). *Migration:* `smd migrate --to 2` (and `smd fmt`) writes each closing fence with its container's colon count, so spec v2 pairs it as v1 does; v1 documents are unaffected.
- **Spec v2 shows text as written: no typographic replacements unless `typography: true`, and only GFM autolink literals are links** (SPEC.md §4.8; spec v2 RFC, proposal 8), in `smd: 2` documents only. The change is visual: the same elements and classes, different characters and fewer links. Straight quotes stay straight, `--` and `---` stay dashes, `...` stays three dots and `(c)`, `(r)`, `(tm)` and `+-` stay as typed, everywhere text is shown: paragraphs, headings, tables, container titles, inline directive content, the header's title and summary, included text, the preview, `smd export` (HTML, PDF, Word, Confluence, Notion), `smd build`, the Block Editor, the MkDocs plugin and the markdown-it, remark and rehype plugins. Only `http://`, `https://`, `ftp://` and `mailto:` URLs, `www.` (lower case) and e-mail addresses become links; a bare domain (`example.com`, `README.md`) and `//host` are text, while `www.` before a top-level domain linkify doesn't know (`www.shop.test`) is now a link, as on GitHub. The markdown-it plugin applies this to spec v2 documents whatever the host's `typographer` and `linkify` say, but only takes away: a host with them off keeps them off. The agent view, `smd export --to md`, tasks and query already showed the source text and don't change. Documents without `smd: 2` render as before. *Migration:* add `typography: true` (`smd migrate --to 2 --keep-typography` does it) to keep curly quotes and dashes; `--link-domains` keeps bare domains linked, written as `[example.com](http://example.com)`. A document migrated with both renders under v2 as it did under v1, apart from what the plan's notes name.
- **`:::include` `section=` matches exactly in `smd: 2` documents** (SPEC.md §3.4; spec v2 RFC, proposal 9). It names a heading by its id (`refunds`, `#refunds`) or its whole text in any case (`Refunds`, `REFUNDS`). A part of a heading's text no longer matches: `section="refund"` used to include `## Refunds`, and now shows the include's fallback, as for any missing section, and `smd validate` reports the warning `include/missing-section` instead of the info `include/section-match`. The including document's version decides, for nested includes too. Rendering, the markdown-it plugin, the agent view, `smd export` (every format), the Block Editor and the validator agree. `smd agent --section` keeps matching a part of a heading: it is an option for people, not document syntax. Documents without `smd: 2` match as before. *Migration:* `smd migrate --to 2` rewrites `section=` to the heading's id (it needs to read the included file), so the document includes the same section under v2.
- **Front matter values keep their YAML spelling in `smd: 2` documents** (SPEC.md §4.7; spec v2 RFC, proposal 10). `{{key}}` and the page header (version, updated, owners and tags; the agent view's header lists every key) show a plain number or boolean as written in the YAML: `version: 2.10` shows `2.10` and the header `v2.10` (they showed `2.1` and `v2.1`), `build: 007` shows `007`, `beta: True` shows `True`, in lists and nested keys too. Quoted and block values and dates show as before. Rendering, the markdown-it plugin (with `frontMatter: true`), the agent view, `smd export` (every format), `smd tasks`, `smd query`, `smd meta`, the Block Editor and the editors' hovers agree. Documents without `smd: 2` show the values as YAML reads them, as before. *Migration:* `smd migrate --to 2` notes each value that shows differently; `--quote-variables` quotes a top-level one (`version: "2.10"`), so every version, v1 tools included, shows it as written. A value in a list or a nested key is a note to quote by hand.
- **Spec v2: a heading's trailing `{}` or `{word}` is heading text** (SPEC.md §4.2.2; spec v2 RFC, proposal 5), in documents with `smd: 2` only. A trailing `{…}` is the heading's attribute list only when it has items and each is `#id`, `.class` or `key=value`; `## Returns {ok}` now reads "Returns {ok}" with the id `returns-ok` (it read "Returns", `#returns`), and `## Object {}` reads "Object {}" with the id `object-`. One bare word makes the whole list text (`## Mixed {#m ok}`), and `{agent}` no longer sets `data-agent`. Rendering, heading ids, the outline, the agent view, `smd to-md`, task sections, `smd fmt` and the validator all read it so; the 1.10 hint `heading/attrs-text` is not reported in such documents, since there the braces are text. Documents without `smd: 2` keep the v1 reading. *Migration:* remove the braces or the bare words if the heading should read as before (the `heading/attrs-text` quick fix in a v1 document); `smd migrate --to 2` does it, and writes `{agent}` as `{agent=true}`. Links to the old ids change with them.
- **Spec v2: `\\` in a quoted attribute value is one backslash** (SPEC.md §5; spec v2 RFC, proposal 6), in documents with `smd: 2` only. `title="\\server\share"` is now `\server\share`, and a value that ends in a backslash is written `"C:\docs\\"`; `"C:\docs\"`, which 1.10 read without escapes, no longer parses (an `attrs/syntax` error, and the item renders as text). Every other backslash is still literal, so `"C:\Users\plan.smd"` is unchanged, and `\"`/`\'` work as in 1.10. In such documents `smd fmt`, the Block Editor's forms and the attribute quick fixes write a backslash as `\\` where one alone would go with the next character (before the closing quote, at the end, or in a run). Documents without `smd: 2` keep 1.10's reading. *Migration:* double the backslashes of a run (`\\\\server`) and write a final backslash as `\\`; `smd migrate --to 2` does it (a new "Backslashes in attribute values" step).
- **Spec v2: any `:name[content]{attrs}` is an inline directive** (SPEC.md §4.2, §10; spec v2 RFC, proposal 7b), in documents with `smd: 2` only. A name outside the vocabulary, such as `:abbr[HTML]` or `:sep{.wide}`, was text; it now renders its content as inline Markdown in `<span class="smd-directive smd-directive-<name>">`, with `.class`, `#id` and the style keys applied as on a styled span, and the agent view, `smd to-md` and the exports show the content. `10:30`, `note:[x]`, code and `\:name[…]` stay text. Documents without `smd: 2` keep it as text. *Migration:* escape a colon that should stay text, `\:abbr[HTML]`, which CommonMark shows as `:`; `smd migrate --to 2` does it.
- **Spec v2: directive names are read in any case** (SPEC.md §4.2; spec v2 RFC, proposal 11), in documents with `smd: 2` only: `:Badge[x]` is `:badge[x]`, `:Due[2026-11-01]` is a due date for `smd tasks`, and `:Ref[fig]` a figure reference. It was text. `smd fmt` keeps the case as written. Documents without `smd: 2` read only lower-case names. *Migration:* escape it (`\:Badge[x]`) to keep the text; `smd migrate --to 2` does, since v1 shows it as text. To make it a directive, write it as you mean it.
- *Which `smd validate` runs newly fail:* documents with front matter that doesn't parse already failed. Documents with a duplicate attribute, a container title conflict, a Mermaid syntax error or an invalid figure `kind` now fail; with `--strict`, so do documents with `priority` on `:::agent`, a suppression comment naming a removed code, or an `smd` value that isn't a whole number. `smd validate --fix` (or `smd migrate --to 2`) fixes everything but the Mermaid errors.
- **New documents are spec v2: `smd init`, `smd from-md` and the other writers write `smd: 2`** (SPEC.md §10; spec v2 RFC, "Rollout and migration"). The 13 templates of `smd init` (and the writer skill), `smd from-md` and VS Code's **Convert Markdown File to .smd**, `smd decisions --md`, `smd report`, `smd tasks --gantt --smd`, the front matter snippet and the playground's starter document say `smd: 2` (they said `smd: 1`, or nothing for the Gantt document), so new documents get the v2 rules: text as written, without curly quotes or dashes unless `typography: true`, only GFM autolinks, and the other rules above. The templates show what they showed, with straight quotes. `smd from-md` keeps how GitHub shows the Markdown: it puts multi-line `$$` delimiters on lines of their own and escapes a literal `:name[…]` outside the vocabulary (`\:abbr[HTML]`), which spec v2 would read as a directive; a `.md` file whose front matter already has an `smd` key keeps it. The npm package's `SMD_VERSION`, the version writers write, is 2. **Existing documents are unaffected:** they keep their `smd` line, and the tools that add front matter to an existing document keep the rules it is read with: the `frontmatter/version` fix still adds `smd: 1`, and Set Document Status adds `smd: 2` only to a document that spec v2 reads as v1 does (else `smd: 1`). *Migration:* nothing for existing documents. To keep the v1 rules in a new document, write `smd: 1` in it (or change the template's line); to move existing documents to spec v2, run `smd migrate <files|dirs> --to 2` (see Added), and `--check` in CI.
- **Node.js 22 or newer** (spec v2 RFC, "Tool and API changes"): Node 18 and 20 are past their end of life. The npm package and the pre-commit hooks' `package.json` say `engines.node: ">=22"`; the `validate` GitHub Action stops with "Node.js 22 or later is required" (exit 2) on an older Node; the MkDocs plugin stops a build with "Node.js 22+ is needed". The CLI bundles (`smd`, `smd.cjs` and the MkDocs bridge) are built for Node 22. *Migration:* install Node.js 22 (an LTS release) or newer; in GitHub Actions, add `actions/setup-node` with `node-version: 22` before `bislink360/styled-markdown/validate` when the runner's Node is older.
- **VS Code 1.97 or newer** for the extension (`engines.vscode: ^1.97.0`; it was 1.90). Pasting an image into a `.smd` file, which needed 1.97, is now always on. *Migration:* update VS Code (or Cursor, VSCodium, Windsurf) to a release based on VS Code 1.97 or later; older editors keep the 1.x extension.
- **npm: `inlineText(line, options)` takes its options as one object** (spec v2 RFC, "Tool and API changes"), instead of five positional arguments after the line, which were hard to extend. The fields are `today`, `openTask`, `figures`, `variables` and `math`, all optional, as before; the new `InlineTextOptions` type describes them. A call with the old arguments is a TypeScript error, and in JavaScript a `TypeError` that shows the new call (a second argument that isn't an object, such as a date string); `inlineText(line)` is unchanged. *Migration:*
  ```ts
  // 1.x
  inlineText(line, '2026-10-15', true, figures, frontMatter);
  inlineText(title, undefined, false, undefined, frontMatter);
  // 2.0
  inlineText(line, { today: '2026-10-15', openTask: true, figures, variables: frontMatter });
  inlineText(title, { variables: frontMatter });
  ```
- **npm: the vocabulary is read-only** (spec v2 RFC, "Tool and API changes"). `CONTAINERS`, `INLINE_DIRECTIVES`, `NAMED_COLORS`, `CALLOUT_TYPES`, `FRONTMATTER_KEYS`, `STYLE_KEYS` and every other table the package exports from its vocabulary (`DECISION_STATUS`, `RISK_LEVELS`, `RISK_STATUS`, `HTTP_METHODS`, `PRIORITY_VALUES`, `FIGURE_KINDS`, `SIZE_VALUES`, `WEIGHT_VALUES`, `FONT_VALUES`, `ALIGN_VALUES`, `TEXT_STYLE_VALUES`, `VARIABLE_SYNTAX`, `STATUS_VALUES`, `AUDIENCE_VALUES`, `MERMAID_TYPES`) are frozen, nested objects and arrays included, and typed `Readonly`/`readonly string[]` (`ContainerSpec` and `InlineDirectiveSpec` have `readonly` fields). Changing one changed it for every caller in the process, the renderer and validator included. Now an assignment, `push` or `delete` on one is a TypeScript error, and at run time a `TypeError` in strict mode (ES modules, classes, TypeScript output) or silently ignored in sloppy scripts. Reading them is unchanged. *Migration:* copy before changing, and pass a `readonly` array where a function wants `string[]` with a copy:
  ```ts
  // 1.x
  CONTAINERS.mine = { description: 'My block' };
  NAMED_COLORS.push('brand');
  // 2.0
  const containers = { ...CONTAINERS, mine: { description: 'My block' } };
  const colors = [...NAMED_COLORS, 'brand'];
  ```
- **VS Code: the built-in Markdown preview applies `.smd` syntax only to `.md` files that opt in** (spec v2 RFC, "Tool and API changes"). Since 1.6 `smd.markdownPreview.enabled` (default `true`) gave every `.md` file's preview `.smd` syntax, `{{key}}` substitution included, so plain Markdown that happened to contain `{{name}}`, `:::` or `:word[…]` changed. The setting is now `"opt-in"` (the default), `"always"` or `"never"`: with `opt-in`, only a `.md` file whose front matter has an `smd` key (`smd: 1` or `smd: 2`) gets the syntax; other files render as VS Code renders them. The 1.x values still work: `true`, when you set it yourself, is `always`, and `false` is `never` (the settings editor asks you to pick one of the new values). `.smd` files and the Styled Markdown preview are unaffected. *Migration:* add `smd: 1` to the front matter of the `.md` files that use `.smd` syntax (`smd migrate --to 2` doesn't touch `.md` files):
  ```yaml
  ---
  smd: 1
  ---
  ```
  or set `"smd.markdownPreview.enabled": "always"` to keep the 1.x behaviour for every `.md` file.

An option you pass wins over the preset's (`{ preset: 'smd', sourceLines: false }`). Raw HTML and code highlighting stay your instance's: give it `html: true` and a `highlight` function for those, as `renderSmd` has. Without a preset nothing changes. (Spec v2 RFC, "Tool and API changes".)
- npm: the `ReadFile` type, `(relativePath: string, env?: unknown) => string | undefined`, for `renderSmd`'s and the markdown-it plugin's `readFile`, and the `InlineTextOptions` type.
- `smd export <file> --to <format> [-o <file>]` is the one export command (spec v2 RFC, "Tool and API changes for 2.0"). The formats are every single-document export the CLI has: `html` (what `smd render` writes), `md` (`smd to-md`), `pdf`, `docx`, `confluence` and `notion`, each with its own options as before (`--lang`, `--format` and `--landscape` for PDF, `--pandoc`, `--reference-doc` and `--html-only` for Word) and the same output, byte for byte. Without `--to`, the extension of `-o` picks the format: `.html`, `.md`, `.pdf` or `.docx`, in any case; `--to` wins when both are given (so `--to docx --html-only -o page.html` still writes Pandoc's HTML). No format, an empty or unknown one, or an `-o` extension that names none is a usage error (exit 2) that lists the formats, with a "did you mean" for a near miss. `smd export --help` lists every option. `smd --help` lists `smd export` with its formats instead of the separate commands, and a line naming the older ones. `smd build` stays its own command, since it writes a site from a folder, not a file. Nothing changes in the VS Code extension, whose export commands don't go through the CLI.
- `smd: 2` selects spec v2. Every reader (rendering, the agent view, `smd to-md`, tasks, query, the validator, `smd fmt`, the Block Editor and the exporters) now knows a document's spec version: `smd: 2` (or `"2"`) is v2; `smd: 1`, no `smd` key and any invalid value are v1; a newer version (`smd: 3`) is read with the newest rules, v2, with a warning, so the document stays readable. `smd: 2` is no longer an "unsupported version" warning. The version alone changes nothing; the rules that differ by version are listed in SPEC.md §10 (see Breaking changes), which says how the version is chosen. (Spec v2 RFC, versioning rules.)
- A `spec: 1 | 2` option on `renderSmd`, the markdown-it plugin and the remark and rehype plugins, for hosts that can't see the front matter. The document's own `smd` wins over it; it only decides for a document without an `smd` key. The markdown-it plugin reads `smd` from the source's front matter, or from front matter passed as `env.smdVariables`, and puts the version on the render's env as `smdSpec`. `renderSmd` returns the version as `spec`, and the remark plugin puts it in `file.data.smd.spec`.
- `specVersion(text)` (also `specVersion(frontMatterData)`) and `LATEST_SPEC` in the npm package: the one function every tool uses to decide a document's spec version.
- Each `smd index` catalog entry has `smd`, its document's spec version (1 or 2). The catalog's own `smd` is the newest spec version the tool knows: 2 (it was 1).
- The front matter JSON schema accepts `smd: 2` (and `"2"`), and completion offers it.
- VS Code: the status bar item's tooltip says "Styled Markdown spec v2 (smd: 2)" for a document that opts in.
- The `typography` front matter key (SPEC.md §2.1, §4.8): `typography: true` turns typographic quotes, dashes and ellipses on in a spec v2 document. It is in the front matter JSON schema, completion and the Block Editor's front matter form. A spec v1 document may have it, without effect (it always has typography) and without a hint.
- In `smd: 2` documents, the `container/colons` warning for a closing fence whose colon count no open container has, with a fix to the count of the container it closes, and the `container/unclosed` warning for a container closed with one around it, with a fix that adds its own closing fence (SPEC.md §7). Folding ranges and the callout refactorings in VS Code pair fences the same way.
- Corpus documents `v2-math.smd` and `v2-fences.smd` pin the spec v2 `$$` and closing fence rules.
- `directive/unknown` (a warning) covers every inline directive outside the vocabulary in a document with `smd: 2`: "Unknown inline directive ":abbr". It renders as its content, in a plain span.", with a quick fix when a known name is close (`:badg` → `:badge`). Invalid style values on such a directive are `attrs/value` errors, as on a styled span; other keys are not reported, since a later release may define them. In documents without `smd: 2` it still flags only a `:name[…]` close to a known name. (Spec v2 RFC, proposal 7b.)
- The Block Editor offers a form for a spec v2 directive outside the vocabulary: its text, and the color, background and border a styled span's form has. Its attribute and inline forms write values with the escapes of the document's spec version.
- Corpus documents `v2-headings.smd`, `v2-escapes.smd` and `v2-directives.smd` (with `smd: 2`), and `unknown-directives.smd`, the v1 twin of the last, pin the spec v2 inline rules; `migrate.smd` gains a case for the new migration step.
- **`smd migrate <files|dirs> --to 2` writes the migration** (SPEC.md §10.1; spec v2 RFC, "Rollout and migration"); 1.10 only reported it with `--dry-run`, which stays as it is. It writes only `.smd` files whose plan changes something, so a file that already says `smd: 2` is left alone and running it twice changes nothing; a file argument that isn't `.smd` stops it before anything is written (exit 2). Each file is written whole or not at all, through a temporary file in the same folder renamed over it, with its line endings and final newline as the plan has them, and never through a symbolic link that leads outside the paths given. It prints each file it writes with the notes the plan leaves to you (typography, links in the title or summary, values to quote by hand), then a summary. Then it reads each file back and checks it: a new plan finds nothing left to change, and the file rendered with the v2 rules equals the original rendered with the v1 rules, apart from what the notes and v2-meaning steps say; any other difference (such as text an `:::include` brings in) is a warning on stderr. `--no-verify` skips the check. Exit codes: 0 done or nothing to do, 1 a file could not be written (it is left as it was) or a link leads outside the paths given, 2 a usage error.
- `smd migrate --to 2 --check` writes nothing, lists the files that still need migrating and exits 1 if there are any, for CI (as `smd fmt --check`). `--json` reports the plan with `--dry-run` or `--check`.
- VS Code: **Styled Markdown: Migrate to Spec v2** applies the plan of `smd migrate --to 2` to the open document as one edit, which Undo reverts, saves nothing, and shows the report with its notes in the output panel. **Preview Migration to Spec v2** offers **Apply**, which does the same.

- Validation: nothing inside an indented code block, `$$` display math or `$inline math$` is checked as text, as in fenced code. A link, reference, footnote, `:ref[id]`, attribute list, directive or open task written there used to be reported as if it were syntax: `$\sqrt[3]{x}$` gave `attrs/unknown`, and `[a]{color=nope}` in an indented code example gave an `attrs/value` error, which fails `smd validate`. Code and math are found as rendering, the agent view and `smd to-md` find them. No document gets a new diagnostic from this; the false ones are gone.
- Validation: `{{name}}` in an indented code block is no longer reported as `variable/undefined` or `variable/not-text`. Code is never substituted, and fenced code was already left alone.
- `smd tasks`, `smd meta`, `smd query task`, `smd issues`, `smd report`, the site dashboard and the Tasks view in VS Code: a `- [ ]` or `- [x]` line in an indented code block is code, not a task, as in fenced code. A nested task (indented under its parent) is a task as before. Library: `extractTasks`, and the task counts of `getDocumentInfo`, leave lines of code out.
- Release tooling: a `.vsix` built on a developer's machine could pack a local coverage report (`coverage/`) or a downloaded VS Code (`.vscode-test/`); both are now excluded, and the release workflow fails if a `.vsix` holds sources, tests or local output. The published 1.7.0 package was built from a clean checkout and was not affected.

## 1.6.0 — 2026-10-05

The block's body is fallback text, shown only when the file can't be included and by tools before 1.6 (which render the block as a plain box), so a link to the file makes a good body. ### Added
- **GitHub Action** `bislink360/styled-markdown/validate@v1.5.0` (in this repository's `validate/` folder): validates `.smd` files on pull requests, shows each problem as an inline annotation and writes a job summary (counts per severity and the first 50 problems, linked to their lines). It runs the bundled CLI with the runner's Node.js 18+, without installing anything. Inputs: `paths` (one per line, spaces allowed), `fail-on` (`error`, `warning` or `never`), `strict`, `config`, `mermaid`, `stale-after`, `summary` and `cli`.

- **Pre-commit hooks:** the repository is now a [pre-commit](https://pre-commit.com) hook repository (`.pre-commit-hooks.yaml`) with `smd-validate` (fails on errors; `args: [--strict]` for warnings too), `smd-fmt` (formats the staged `.smd` files in place) and `smd-fmt-check` (fails on unformatted files without changing them). - npm: a **markdown-it plugin**, `styled-markdown/markdown-it` (ESM and CommonJS, with types), so any markdown-it 13 or 14 host renders `.smd` syntax: `md.use(smd, options)`. It adds rules to the host's own instance (never a second markdown-it), keeps the host's options, other plugins and code highlighting, and leaves plain Markdown unchanged. Options turn containers, inline directives, attribute lists, `==marks==`, math, task lists and `.smd` code fences on or off (all on by default), and opt into code frames, heading ids, `data-line` source lines and the front matter header; `agentBlocks`, `readFile` (embeds, off unless given) and `today` work as in `renderSmd`. markdown-it is an optional peer dependency: the package keeps zero runtime dependencies. Style the output with `styled-markdown/smd.css`. `renderSmd` uses the same rules, and its output is unchanged.
- VS Code: `.md` files that use `.smd` syntax render in VS Code's **built-in Markdown preview** (containers, directives, attribute lists, marks, Mermaid diagrams, code titles and embeds; math stays VS Code's own while `markdown.math.enabled` is on). New setting `smd.markdownPreview.enabled` (default on). Opening a Markdown preview now activates the extension.
- npm: **remark and rehype plugins** for Astro, Docusaurus, Next.js and other unified pipelines: `import { remarkSmd } from 'styled-markdown/remark'` (or `rehypeSmd` from `styled-markdown/rehype`). They render the whole file with `renderSmd` into one raw HTML node, so the output matches `smd render`; the page loads `styled-markdown/smd.css`. Options: `test` (which files), `header: false` (no title header), `frontMatter` (front matter the host already removed; Astro's is found automatically), `readFile` (embeds, with the file), plus `allowHtml`, `agentBlocks`, `today`. `file.data.smd` holds the front matter and headings. Works with `.md` files; `.mdx` files can't hold `.smd` syntax, because MDX parses `{…}` as JSX first. No new dependencies. Also exported from the main entry, with `renderSmdFile(file, options)`.
- **`smd build <dir> [--out site] [--title "…"] [--base /docs/] [--md] [--clean]`**: a static docs site. Every `.smd` file (and `.md` with `--md`) becomes a page in the same folder structure; `index.html` is the folder's `index.smd` or `README`, else a generated index of every document. Links between documents point at their pages (anchors kept, external links untouched) and linked local files such as images are copied, so the site works from disk and from any static host (`--base` for absolute links). Pages get a sidebar ordered by title, breadcrumbs, previous/next links, backlinks ("Linked from"), a client-side search box (an index of titles, headings, summaries and section excerpts in `_smd/search-index.js`, no external service) and a link to `dashboard.html`: open tasks (overdue first), decisions and open risks with the impact × likelihood matrix across the site. Stylesheet and scripts are written once to `_smd/`; only pages with diagrams or math load Mermaid and KaTeX from a CDN. `--out` must be outside the source folder and new, empty or a previous build (recognized by its `.smd-site.json`), and `--clean` deletes only the files that build recorded.

The protocol is implemented in the CLI itself (Content-Length framed JSON-RPC over stdio, no new dependencies); positions are UTF-16 columns as LSP specifies, or UTF-8/UTF-32 when the client offers only those. Logs go to stderr. Other transports (`--socket`, `--pipe`, `--node-ipc`) exit with code 2. The VS Code extension is unchanged.

- Library: `querySmd(source, selector, options)`, `parseSelector` and `SelectorError`.
- `smd index <files|dirs…> [-o catalog.json] [--compact]` writes a JSON catalog of every document for agent routing:
  - per document: path (relative to the working directory, `/` separators), title, summary, status, owners, tags, audience, updated, related, and token costs of the file and of its full agent view
  - sections with level, text, id, zero-based line range and agent-view token cost (the numbers `smd outline` shows)
  - counts: open, done and overdue tasks, decisions by status, risks and open risks, questions, API endpoints, diagrams and `:::agent` blocks
  - deterministic output (no timestamps, sorted by path) so the catalog can be committed and diffed; `--today` pins the overdue count
- Library: `indexEntry(source, path, options)` and `smdIndex(documents, options)`, with the `SmdIndex*` types.
- `smd diff <old.smd> <new.smd>` and `smd diff <files|dirs…> --since <git-ref>` show only what changed, for an agent catching up on a document:
  - front-matter changes (`status: draft → accepted`), then changed, renamed and added sections in the agent view of the new version (line refs point into the new file), then removed sections (heading and old lines only)
  - sections are matched by heading id, then by content, so a renamed heading is reported as a rename; a change is shown in the smallest section that contains it, without unchanged subsections; content before the first heading counts as a section
  - only changes visible in the agent view count: styling, comments and `:::human` content are ignored, and sections marked `{agent=skip}` are listed without their content
  - `--since` compares each file with its version at a commit, branch or tag (via `git show`), and also reports files added and deleted since; stderr shows the token cost against the full agent view
  - `--json`, `--brief` and `--no-lines` work as in `smd query`; the exit code is 0, or 1 with `--exit-code` when something changed (like `git diff --exit-code`)
- Library: `diffSmd(oldSource, newSource, options)`.
- `smd outline <file> --related` adds a block listing the documents in front matter `related:`: each `.smd` file's title, status, summary and full agent-view token cost, so agents can decide whether to open it. URLs and other files are listed but not read; missing files and files outside the project folders are marked. Without the flag the outline is unchanged.
- The reader skill and `docs/AGENTS.md` tell agents to check related documents with `smd outline --related` and to open them only when the question needs it.
- Library: `relatedDocs(source, { readFile })`, `relatedEntries`, `summarizeSmd` and `formatRelated`.
- `smd agent --max-tokens N` fits the agent view into a token budget. It first condenses the view as `--brief` does, then leaves out whole sections, least important first, and puts a one-line pointer in each one's place: `[section omitted: ## Rollout plan, L153-L166, ≈118 tokens — smd agent plan.smd --section "Rollout plan"]`.
  - never left out: the header (title, front matter, summary), text before the first `##` section, sections with `:::agent` instructions, and sections requested with `--section`
  - kept longer: sections with a danger or warning callout, an accepted decision, a question or an open task; among the rest the deepest headings go first, then the largest, then the latest
  - stderr says what was condensed and left out and the final size; when even the smallest view is over the budget it is printed anyway with a warning (exit code 0)
  - without the flag the output is unchanged
- `--tokenizer o200k_base|cl100k_base|p50k_base|r50k_base` on `smd agent` and `smd outline` shows exact token counts next to the estimate (`≈1531 est · 1402 o200k_base tokens`), and `--max-tokens` then counts with it. It uses the `js-tiktoken` package if you have installed it in your project or globally; smd still has no runtime dependencies and says how to install it when it is missing. These are OpenAI encodings: there is no public tokenizer for current Claude models, so for Claude the counts are still approximate.
- Library: `agentView` options `maxTokens`, `tokenizer` (any `{ name, count(text) }`) and `file` (used in the pointers), result fields `budget` and `counted`, and `outline(source, { tokenizer })`. Types `BudgetResult`, `OmittedSection` and `Tokenizer`.
- `smd skills install --target <claude|cursor|copilot|agents>` sets up agents without Claude-style skills (repeat the flag or separate targets with commas; the default is `claude`, which works as before):
  - `cursor` writes the project rule `.cursor/rules/styled-markdown.mdc` (applies to `**/*.smd`)
  - `copilot` writes `.github/instructions/styled-markdown.instructions.md` (`applyTo: "**/*.smd"`)
  - `agents` adds a section to `AGENTS.md` between `<!-- styled-markdown:start -->` and `<!-- styled-markdown:end -->`; re-running replaces that section and keeps the rest of the file
  - each also installs the CLI once to `.smd/smd.cjs`, and the rules tell agents to run `node .smd/smd.cjs`
  - `--dir` sets the project root for these targets; `--global` and `--only` apply to `claude` only
- All three targets share one set of reading and writing rules, `skills/agent-rules.md`.
- Six new templates for `smd init --template` and the writer skill, 13 in total:
  - `postmortem`: blameless incident review with impact metrics, timeline, root cause, action items with owners and due dates, and rules for agents doing the follow-ups
  - `release-notes`: highlights, breaking changes with migration steps, deprecations, Added/Changed/Fixed, upgrade and known issues
  - `okrs`: objectives with key-result tables (owner, baseline, target, progress, confidence), initiatives and risks
  - `onboarding`: day-one setup, first-week tasks, a 90-day timeline, key links and people to meet
  - `test-plan`: scope, strategy, environments, test cases, entry and exit criteria, risks and schedule
  - `pr-description`: summary, changes, testing, risk and rollback, checklist and review focus
- More diagnostics carry a machine-applicable `fix` (quick fix in VS Code, `fix` in `--json`, applied by `smd validate --fix`). A fix is attached only when there is one clear repair:
  - `frontmatter/status`, `frontmatter/audience`, `frontmatter/value`: the one close allowed value (`aproved` → `approved`, `Dark` → `dark`)
  - `frontmatter/accent`: a misspelled named color (`bleu` → `blue`)
  - `frontmatter/type`: `yes`/`no`/`on`/`off` or a quoted `"true"`/`"false"` on a true/false key → `true`/`false`
  - `frontmatter/date`: year-first dates with other separators or no zero padding (`2026/9/5` → `2026-09-05`)
  - `container/unclosed`, `fence/unclosed`: add the closing line at the end of the document, where the block already ends (unindented blocks only)
  - `attrs/unknown`: the one close accepted attribute name, when it is not already set (`{colr=red}` → `{color=red}`)
  - `attrs/value`: the one close allowed value for block and directive enums, named colors, `size`, `weight`, `font`, `align`, `:priority[…]` and heading `agent=skip`; year-first `date="…"` and `:due[…]` dates
- `applyFixes` applies adjacent edits and orders several insertions at the same point innermost block first, whatever order the diagnostics come in.

### Changed
- `smd validate --fix` applies fixes and checks again until nothing is left to fix, e.g. a code block is closed before the container around it. The `fixed` count covers all rounds.

## 1.2.0 — 2026-09-28

No breaking changes. Documents, CLI commands and flags, diagnostic codes, library exports, extension commands and settings from 1.1.0 all keep working, and every document that passed `smd validate` still passes. New checks are warnings or info: `link/undefined-reference`, `frontmatter/value` and `mermaid/syntax` are warnings, `frontmatter/type` now also covers a `title`, `summary` or `version` given as a list or mapping, and `frontmatter/stale` is info. So `smd validate --strict` can report warnings on documents that passed before; turn any rule off in `smd.config.json`.

### Added
- Go to definition (`F12`, `Ctrl+Click`) on links: `#anchor` jumps to the heading, `{#id}` block or HTML element; `other.smd#anchor` opens the other document at that heading; relative files open; `[text][label]` jumps to its `[label]: …` definition.
- Link validation checks anchors in other documents: `[x](plan.smd#rollout)` warns with `link/missing-anchor` when `plan.smd` has no such heading.
- `link/missing-anchor` offers a quick fix to the closest heading id, and also accepts `{#id}` block attributes and HTML `id`/`name` as targets.
- Reference-style links: `[text][label]` without a `[label]: …` definition reports the new `link/undefined-reference` rule, and definition targets are checked like inline links.
- HTML `href`/`src` targets and front matter `related:` entries are checked for missing files and anchors.
- `smd fmt <files|dirs…>` formats `.smd` files in place, with `--check` for CI (exit code 1 when a file isn't formatted) and `--stdout` for one file. It only changes layout, never meaning:
  - container fences: `:::name` with no space, one colon count per nesting level (the innermost uses `:::`, each enclosing level one more, e.g. `::::tabs` around `:::tab`), closing fences matching their opener; unbalanced documents keep their colons
  - attribute lists on containers, headings, `[text]{…}` spans and inline directives: `#id`, `.classes`, then keys in the spec's order; values quoted only when needed (`title` and `label` always); duplicate keys collapsed to the value that wins
  - pipe tables: aligned columns and delimiter rows (wide characters and emoji count as two columns)
  - blank lines around containers, code, math, headings and tables where they touch paragraph text, runs of blank lines collapsed, one final newline
  - code, math, raw HTML, front matter and indented blocks are left untouched
- **Format Document** and format on save in VS Code, using the same rules as `smd fmt`.
- `formatSmd()` in the `styled-markdown` library.
- Path and anchor completion in VS Code:
  - inside links and images `](…`, reference definitions `[label]: …`, front matter `related:` entries and code fence `file="…"` embeds, relative files and folders are suggested (`.smd`/`.md` first; `related:` offers documents only)
  - after `#`, the headings, `{#id}` blocks and HTML ids of the current document or of the linked `other.smd#…` are suggested, using its unsaved text when it is open
  - an empty link target also offers this document's `#anchors`
  - nothing is suggested inside code
- Find references (`Shift+F12`) for heading anchors across the workspace, from a heading or from a link's `#anchor`. The results cover inline links, reference definitions and HTML `href`s in `.smd` and `.md` files.
- Rename a heading (`F2`) and update every link to its anchor across the workspace. When a rename renumbers the anchors of later headings with the same text (`#setup-1` → `#setup`), links to those are updated too. Headings with an explicit `{#id}` keep their anchor, and percent-encoded anchors stay encoded.
- Configurable rules. A `smd.config.json`, `.smdrc` or `.smdrc.json` file in a document's folder or a parent folder turns rules `off` or sets their severity (`error`, `warning`, `info`, `hint`) by code, by category (`link/*`) or for every rule (`*`). The nearest file applies, the search stops at the repository root, and the most specific key wins. It is used by:
  - VS Code, which reloads the file as it changes, reports its problems on the file itself, and completes and checks rule codes from a JSON schema
  - `smd validate` and `smd meta`, which also accept `--config <file>`
  - the library, through `validateSmd(text, { rules })`, alongside the `RULE_CODES`, `readRuleConfig` and `applyRuleSettings` exports
- Inline suppression comments: `<!-- smd-disable-next-line [codes] -->`, `<!-- smd-disable-line [codes] -->` and `<!-- smd-disable [codes] -->` … `<!-- smd-enable [codes] -->`. No codes means every rule. Unknown codes are reported as the new `rules/unknown` warning, with a fix.
- Refactorings in VS Code (`Ctrl+.`):
  - wrap the selected lines in `:::note`, `:::tip`, `:::warning`, `:::danger`, `:::card`, `:::details`, `:::agent` or `:::human`; the new fence gets one more colon than any container inside it, and selections that split a code block or container aren't offered
  - convert a callout to another type, from its opening line
  - convert a blockquote callout into a `:::callout`, from GitHub alerts (`> [!WARNING]`, mapped like `smd from-md`) or bold labels (`> **Warning:**`, `> **Tip**:`); nested quotes keep their extra `>`
- Mermaid syntax errors as warnings (`mermaid/syntax`), on the line and columns the parser points at, e.g. "expected TXT, got end of line". Diagrams are parsed with Mermaid's own parser, which ships as a separate `dist/mermaid-parse.js` and is loaded only when a document has diagrams.
  - VS Code: errors appear as you type, and `smd.validation.mermaid` turns the check off.
  - `smd validate`: `--no-mermaid` skips the check. The single-file CLI bundled in the agent skills doesn't include the parser and skips it.
  - Library: `checkMermaid(text, parse, rules?)` and `mermaidBlocks(text)`; pass `mermaid.parse` or any compatible parser.
  - Like other rules, `mermaid/syntax` can be turned off or given another severity in `smd.config.json` / `.smdrc`, and silenced with `<!-- smd-disable-next-line mermaid/syntax -->`.
- Front matter JSON Schema: one schema (`FRONTMATTER_SCHEMA`) drives front matter validation and editor completion.
  - It is published as `extension/schemas/smd-frontmatter.schema.json` and as `styled-markdown/frontmatter.schema.json` on npm, for YAML tooling and pipelines.
  - Completion now offers every enumerated value, including `theme`, `toc` and `smd`. It skips keys already in the front matter, and suggests today's date for `updated` and `created`.
  - New `frontmatter/value` warning for values the schema doesn't allow on keys without their own rule, such as `theme: neon`.
  - `title`, `summary` and `version` given as a list or mapping are reported as `frontmatter/type`.
- Stale document check `frontmatter/stale` (info): `updated` is more than 180 days old and the status isn't `archived` or `deprecated`. Configure it with `smd.validation.staleAfterDays`, `smd validate --stale-after <days>` or `validateSmd(text, { staleAfterDays })`; `0` turns it off. Like other rules, it can also be turned off or given another severity in `smd.config.json` / `.smdrc`.
- Workspace symbol search (`Ctrl+T`) across every `.smd` file: headings, `:::decision` and `:::risk` titles, and `:::api` endpoints, which are searchable by method and path. Each file's symbols are cached until it changes.
- Hover previews:
  - over a link's text or target, `#anchor` / `other.smd#anchor` shows the start of that section (up to 20 lines), and `other.smd` shows the document's title, status, summary and top-level sections
  - over a ```` ```lang file="…" lines="…" ```` line, the embedded code (up to 30 lines), or why it can't be read
- List continuation on Enter (`smd.editor.continueLists`):
  - tasks continue unchecked and keep their `@owner` mentions, with the cursor before them
  - bullets repeat and numbered items count up
  - Enter on an empty item ends the list
  - nothing changes inside code blocks
- Paste and drag-and-drop images:
  - images are saved to `docs/images/` (`smd.images.folder`) and linked relative to the document
  - images already in the workspace are linked in place
  - name clashes get `-1`, `-2`…
  - pasting needs VS Code 1.97 or later; dropping works on every supported version
- **Styled Markdown: Set Up Spell Checking (cSpell)** adds an `smd` entry to cSpell's `languageSettings`, so container and directive names, attribute lists, mentions, link targets, front matter and code aren't reported as misspellings. It runs only when you ask, because cSpell settings can't be scoped to a language by another extension.
- `parseSmd(text)` in the library: headings and anchor ids without rendering HTML, parsed incrementally.

### Changed
- Large documents stay responsive. On a 12,000-line document, after typical edits:
  - validation: about 110 ms → 30 ms
  - `smd outline`: 11 s → 80 ms (it transformed the document once per section; now once)
  - `smd meta`: 180 ms → 40 ms
  - the agent view and its token counter: 90 ms → 26 ms
  - Outline view and go to definition: no render at all
  Headings and anchors now come from an incremental parse that reuses every top-level block the edit didn't touch, instead of a full HTML render, and results are identical. Math checks are cached per formula, and the status-bar token counter waits longer before updating on long documents.
- The npm package ships Mermaid's parser for `smd validate` (`dist/mermaid-parse.js`, 3.4 MB unpacked). The library entry points don't load it.
- The preview keeps your place when it updates: the source line at the top of the preview stays there, even when lines are added or removed above it.
- The selected tab in `:::tabs` and opened or closed collapsibles (`:::details`, `collapsible` callouts, agent blocks) stay as you left them across updates. They're matched by their titles, not their position.
- The preview restores its scroll position, tabs and collapsibles after its tab was hidden and shown again.
- Unchanged Mermaid diagrams are restored from the cache right away on each update, instead of waiting behind a diagram that changed and briefly showing their source. A diagram you're editing keeps its previous height until the new version renders, so the page below it doesn't jump.

### Fixed
- The preview's Content-Security-Policy nonce is now generated with a cryptographically secure random source instead of `Math.random()`.
- A lone carriage return (`\r` without `\n`) was treated as a line break, so heading lines in the preview, scroll sync, outlines and `smd meta` drifted from the editor.
- A front matter key containing regex characters, such as `"a(b": 1`, made validation throw.
- The `frontmatter/unknown-key` quick fix no longer rewrites the opening `---` when the key is written differently in YAML (e.g. quoted); it is then offered as a hint only.
- A preview hidden behind another tab showed the document as it was when the preview was opened until the next edit.
- Link targets with spaces in angle brackets (`[x](<my file.md>)`), `'single'`/`(paren)` titles or balanced parentheses were not checked.
- A link with malformed percent-encoding (`[x](#100%)`) made validation throw.
- Links inside `~~~` code fences that contain ```` ``` ```` lines were checked as if they were prose.

### Internal
- CI runs a seeded fuzz test of the core (render, validate, quick fixes, agent view, outline, document info, tasks, Markdown conversion) and a benchmark suite (`npm run bench`) that fails on order-of-magnitude slowdowns.
- CI checks that `examples/` and `docs/gallery/` are formatted (`smd fmt --check`).
- The release check compares a corpus of documents (`extension/test/compat/corpus/`) across releases; it starts with the rule and suppression-comment additions.
